This key stores the text. Press inserts the text below at the cursor; hold the key (~half a second) to capture whatever's currently selected and store that into the key instead of typing it here.

Hold tries to read your selection directly through macOS's Accessibility API first — no clipboard involved — and falls back to ⌘C where that doesn't work (which is most places, including iTerm2, Safari and ChatGPT). Press always goes through ⌘V. So in practice both gestures usually do use your clipboard — but they now save what was on it first and put it back.
Over the 32 KiB limit. Your text is kept exactly as typed — nothing is truncated or deleted — but the key won't paste it until it's shorter.
Putting your clipboard back. Before a gesture takes over the clipboard, everything on it is copied aside — every item and every format, not just the plain text, so an image, a file or rich text survives — and copied back when the gesture is done. What that does not cover, honestly: if something else copies while the gesture is running, that newer copy wins and yours is left alone; a clipboard already marked secret by a password manager is not copied aside at all (duplicating a password is worse than leaving it), so that gesture replaces it as it used to; content generated on demand by another app (a file promise, a big image) is turned into ordinary data, and if it can't be read the clipboard isn't saved; a clipboard larger than 64 MB in total isn't saved either; and after ⌘V there is a short wait before your clipboard comes back, because nothing in macOS says when the app you pasted into has finished reading. If an app reads later than that wait, it pastes your old clipboard instead of the snippet — untick the box above for that key if you ever see it. Your clipboard manager will also record the gesture's writes either way.

The button is the storage — but the clipboard is the delivery mechanism. Capture prefers the direct Accessibility read where an app supports it (standard text fields do; iTerm2, Safari and ChatGPT do not); inserting always uses ⌘V, because the direct WRITE was measured reporting success while inserting nothing, and a confident false success is worse than touching the clipboard. That is why the save-and-restore above exists: the clipboard is unavoidable, so the key borrows it rather than keeping it.

What "hold" refuses, and what it can't catch: capture refuses outright while macOS reports Secure Input is on (a password field is very likely focused) — checked before either route, so it applies whichever one runs. On the clipboard route it also refuses a copy marked by a password manager as concealed. It CANNOT recognise every secret field — one that sets neither signal (plenty don't) is captured like any other text, so don't rely on this as a guarantee around sensitive fields.

What "press" refuses: it checks that the snippet is still the top of the clipboard immediately before sending ⌘V, and refuses (an alert, not a silent paste) if anything else wrote in between — so a clipboard manager can't cause the key to paste someone else's content.

Where this lives: the text above is saved as PLAIN, UNENCRYPTED text in the Stream Deck profile on this Mac — profile export, sync, and backups all carry it in the clear. Use "Clear stored text" to remove it. Only text is ever stored — no images, files, or other clipboard content.

Requires: Accessibility access for Stream Deck (to read/write a selection directly, and to send the ⌘C/⌘V fallback keystrokes), and Automation access for Stream Deck to control "System Events" (macOS will prompt for this the first time; it can't be checked in advance the way Accessibility can).
